## Context

The Zoho Inventory clone (Next.js 16) is functionally complete with all business logic embedded in Next.js: 23 server-action files (~4,100 LOC) + ~60 server components querying Drizzle directly, 59 tables / 21 PG enums in PostgreSQL, no auth, single org. Goal: extract a **separate Go backend** that owns all business logic and the DB, keep PostgreSQL unchanged, and add **Clerk auth** (official `clerk-sdk-go` v2 backend + `@clerk/nextjs` frontend). The UI must keep working throughout → **strangler-fig migration, domain by domain**, with Next.js becoming a thin BFF (server components/actions keep their signatures, internals switch from Drizzle to HTTP calls to Go).

**Note: you will create the backend directory yourself.** All backend scaffolding below goes inside the directory you add (assumed `backend/` at repo root — paths adjust if you place it elsewhere). I will not create or move that directory.

## Key decisions

- **Repo layout**: monorepo — backend Go module lives in the directory you add, alongside the Next.js app. One clone, one CI, shared docker-compose.
- **Go stack — Option A "chi + sqlc"**: `net/http` + `chi`, `pgx/v5` + `sqlc` (your existing SQL in `lib/stock.ts`, `lib/numbering.ts`, `lib/reports.ts` ports almost verbatim into `.sql` query files), `goose` migrations, `shopspring/decimal` for `numeric(14,2)`, `slog`, `go-playground/validator`, `testcontainers-go` for tests.
  - *Alternative B*: **Gin + GORM** — closest to Drizzle DX, fastest CRUD, but ledger/GROUP BY/`UPDATE...RETURNING` queries need Raw() anyway.
  - *Alternative C*: **Huma (OpenAPI 3.1-first)** + sqlc — generates a typed TS client for the frontend; slightly more ceremony.
- **Integration pattern**: Next.js = BFF. Reads: server components replace `db.select()` with a typed Go API client fetch (stays SSR). Writes: `actions/*.ts` keep the same exported signatures but proxy to Go REST endpoints — **~100 call sites keep working unchanged**.
- **Tenancy**: single-org for now with a seam — `organization.clerk_org_id` added; org resolved from the JWT in Go middleware. Adding `organization_id` columns to all 59 business tables is deferred (mechanical migration later).
- **Schema ownership moves to Go**: `goose` migrations; migration 001 generated from current DB (`pg_dump --schema-only`). Drizzle-kit retired after cutover (Drizzle stays only for `db/seed.ts` until then).

## Architecture

```
<backend-dir>/                  # directory YOU create; Go module lives here
├── cmd/server/main.go
├── internal/
│   ├── config/                 # env loading (godotenv)
│   ├── db/                     # pgx pool, sqlc generated code (queries, models)
│   ├── migrations/             # goose SQL files
│   ├── middleware/             # clerk JWT verify, org context, logging, CORS
│   ├── domain/<module>/        # handler + service + repo per domain
│   └── platform/               # numbering, stock ledger, totals, activity log
└── go.mod

lib/api-client.ts               # NEW: typed fetch wrapper to Go (adds Clerk token)
middleware.ts                   # NEW: @clerk/nextjs, protects /office/**
app/, components/, actions/     # unchanged signatures; action internals swapped
```

**Ports to reproduce in Go** (the actual business logic):
1. **Atomic numbering** (`lib/numbering.ts`) → tx: `UPDATE numbering_series SET next_number = next_number + 1 ... RETURNING`, format `PREFIX-00001`
2. **Stock ledger** (`db/schema/warehouses.ts:142`, `lib/stock.ts`) → signed `stock_movements` postings: opening stock, adjustment approve, transfer ship/receive (+/-) + reversal on delete, shipment stock-out + reversal, PO receive stock-in, sales-return stock-in, stock-count → generated adjustment; stock-on-hand = SUM per item+warehouse
3. **Totals** (`computeTotals` in `actions/invoices.ts:29-76`, duplicated in estimates/sales-orders/bills/purchase-orders) → one Go service using `decimal`
4. **Status machines + conversions**: SO→Package→Shipment→Invoice chains copying header+lines and advancing statuses; payment application flipping `partially_paid`/`paid`
5. **Activity log** (`lib/activity.ts`) → insert on every mutation
6. **Documents**: multipart upload to `.data/uploads/` (same disk layout), download streaming — Go takes over the 3 existing route handlers (`/api/search`, `/api/notifications`, `/api/documents/[id]`)

**Auth flow**: `@clerk/nextjs` on the frontend (ClerkProvider in `app/layout.tsx`, sign-in/up pages, `middleware.ts`); server components/actions call the API via `lib/api-client.ts` attaching `getToken()`. Go middleware verifies the Clerk session JWT (`clerk-sdk-go/jwt`), extracts `user_id`/`org_id` into context. Webhook `POST /api/v1/webhooks/clerk` (signature-verified) upserts into the existing `users` table keyed by `clerk_user_id`.

**API contract**: REST JSON at `/api/v1/*`. Error shape matches today's action contract (`{ ok, errors }` with per-field messages) so thin proxies map 1:1; zod schemas in `lib/schemas/` stay as client-side validation, Go adds server-side validation.

## Phases (each leaves the app fully working)

- **Phase 0 — Foundation**: scaffold inside your backend directory (chi + sqlc + goose config), migration 001 from pg_dump, health endpoint, pgx pool; docker-compose (postgres + backend); Clerk integration on Next (provider, middleware, sign-in pages) + Go JWT middleware + webhook sync; `lib/api-client.ts`; org gets `clerk_org_id`.
- **Phase 1 — Master data**: items, item-groups, composite-items, price-lists, contacts, warehouses, settings (taxes/currencies/units/brands/categories/numbering series).
- **Phase 2 — Inventory ops**: adjustments, transfers, stock-counts + the stock ledger service and stock queries.
- **Phase 3 — Sales chain** (hardest, after patterns are proven): estimates, sales-orders, packages, shipments, invoices, customer payments, credit notes, sales returns — status machines, conversions, `computeTotals`.
- **Phase 4 — Purchases**: purchase-orders, bills, vendor payments, debit notes, expenses.
- **Phase 5 — Cross-cutting**: dashboard, reports, global search, notifications, activity history, documents upload/download.
- **Phase 6 — Cutover cleanup**: delete Drizzle query code from pages/actions, retire `drizzle-kit`, keep `db/seed.ts` until re-ported.

## Verification

- **Unit/integration (Go)**: `testcontainers-go` Postgres; test ledger postings (adjustment/transfer/shipment reversals), numbering uniqueness under concurrency, computeTotals fixtures, payment status transitions.
- **E2E**: run `bun dev` + `go run ./cmd/server`; click through: create item → SO → package → shipment (verify `stock_movements` rows) → invoice → payment → status flips; adjustment changes stock-on-hand.
- **Parity check**: before swapping each domain, run old action and new endpoint against same input; diff DB rows.
- Clerk: sign in, confirm Go validates the JWT and logs `user_id`; webhook creates the `users` row.
